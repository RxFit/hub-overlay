Left-panel 07 — Unify the panel → chat inject path P1

Summary. The left panel's "tap-to-inject" path (handleChatInject) calls sendToApi(...) directly, bypassing doSend — the path that every typed/suggestion message takes. As a result, panel-injected messages never run detectIntent, role-gating, interview-advance, or quoted-reply prefixing. The most visible symptom: tapping the Tasks "+ Task" affordance injects "I want to create a new task in my … list", but Interview Mode never activates — even though typing that exact sentence would activate it. This piece routes action-style injects through the shared doSend core while keeping read-style ("tell me about…") injects on the direct, intent-free path, then cleans up three related defects on the inject path (signature drift, an un-capped attachment count, and a misleading wire payload).

Verification note (against current master, tip f8ae3ad, after PRs #14–#19 / plans 01–06). All four findings were re-confirmed present on master. None were already fixed by plans 01–06. Line numbers in the original brief had drifted substantially (the file grew via plans 01, 02, 05, 06); every line reference below is the corrected, current value. The one cross-cutting interaction with prior work: plan 01 rewrote sendToApi's error handling (the structured !res.ok branch and the streamed parsed.error append), which moved the wire-payload block — accounted for in finding 4 below. Plan 06's StrictMode "pure updater / deferred side-effects" refactor of doSend is the structure we extend in finding 1.

Why this matters

  • Feature parity is silently broken. Two visually identical user actions (tap the "+ Task" chip vs. type the same words) take divergent code paths and produce different products. The chip never enters Interview Mode, so the user gets a free-text chat answer instead of the guided create-task flow with its confirm card and write-boundary gate.
  • Security/consistency surface. The direct inject path skips hasPermission(userRole, intent) role-gating that doSend applies. Today that only matters for action prompts, but any future panel affordance that injects a privileged action would bypass the gate by construction.
  • Attachment cap is enforced in two of three places. The 5-attachment cap exists server-side and in the manual add path, but the inject path forwards an unbounded array. A panel that injects >5 attachments would send them all to the client buffer and rely solely on the server slice — defense-in-depth is broken.
  • Type drift hides bugs. Three of four left-panel section props are typed (msg: string) => void while they actually receive a handler that accepts attachments. The compiler can't catch a section that forgets to forward attachments.

Change 1a — Route execute injects through doSend

File: hub/app/page.tsx — handleChatInject (lines 1027–1051).

Rationale. doSend already encapsulates the full send pipeline (quoted-reply prefix, the StrictMode-safe pure-updater append, intent detection / role-gating / interview branching, and the deferred sendToApi). Rather than duplicating that tail, delegate to it for action injects. Because doSend hardcodes useCase='deep_dive' in its sendToApi calls (lines 728, 731, 995), an execute inject that does not match an intent will fall through to a normal deep_dive chat send — acceptable, and identical to what a user typing the same words gets today. The mobile-drawer-closing side effects unique to injects stay in handleChatInject.

/* ── Handle context injection from panels ── */
const handleChatInject = useCallback((message: string, useCase: string = 'deep_dive', injectAttachments?: ChatAttachment[]) => {
  setMobileLeftOpen(false)
  setMobileRightOpen(false)
  setMobileTab('chat')
  const userMsg = {
    id: crypto.randomUUID(),
    role: 'user' as const,
    content: message,
    timestamp: new Date().toISOString(),
    attachments: injectAttachments && injectAttachments.length > 0 ? injectAttachments : undefined,
  }
  let updatedMessages: ChatMsg[] = []
  setMessages(prev => {
    updatedMessages = [...prev, userMsg]
    return updatedMessages
  })
  sendToApi(message, updatedMessages, useCase, injectAttachments)
}, [sendToApi])
/* ── Handle context injection from panels ──
 * Two routing modes:
 *  - 'execute'  → action-style inject: delegate to doSend so detectIntent,
 *                 role-gating, and Interview Mode run exactly as if the user
 *                 had typed the sentence (parity with handleSend).
 *  - other      → read-style inject ('recall' / 'deep_dive'): keep the direct
 *                 sendToApi path (no intent detection on informational lookups).
 */
const handleChatInject = useCallback((message: string, useCase: string = 'deep_dive', injectAttachments?: ChatAttachment[]) => {
  setMobileLeftOpen(false)
  setMobileRightOpen(false)
  setMobileTab('chat')

  // Defense-in-depth: mirror the 5-attachment cap enforced in handleAddAttachment
  // and server-side (route.ts). The inject path previously forwarded these uncapped.
  const cappedAttachments = injectAttachments && injectAttachments.length > 0
    ? injectAttachments.slice(0, 5)
    : undefined

  // Action-style injects go through the shared send core for full parity.
  if (useCase === 'execute') {
    doSend(message, cappedAttachments)
    return
  }

  // Read-style injects: direct, intent-free send (unchanged behavior).
  const userMsg: ChatMsg = {
    id: crypto.randomUUID(),
    role: 'user' as const,
    content: message,
    timestamp: new Date().toISOString(),
    attachments: cappedAttachments,
  }
  let updatedMessages: ChatMsg[] = []
  setMessages(prev => {
    updatedMessages = [...prev, userMsg]
    return updatedMessages
  })
  sendToApi(message, updatedMessages, useCase, cappedAttachments)
}, [sendToApi, doSend])
Ordering note for the coding agent. doSend is declared (line 652) before handleChatInject (line 1027), so referencing it is safe. Add doSend to the dependency array (shown above). Both are useCallbacks; doSend's identity is stable except when its own deps change, which is correct.

Change 1b — Re-point the Tasks "+ Task" create prompt to the action path

File: hub/app/components/LeftPanelSections.tsx (line 356) and hub/app/page.tsx wiring.

Rationale. The "+ Task" affordance currently rides injectRecall (useCase='recall') because the whole left panel is wired to one handler. With the decision rule from Change 1a, an inject only enters Interview Mode when its useCase is 'execute'. There are two viable approaches; pick Approach A (minimal, surgical):

Approach A — give the create affordance its own execute handler. Thread a second, optional prop (e.g. onInjectAction) into TasksSection for the create button only, wired to injectExecute in page.tsx, while the per-row "tell me about" taps keep onInjectChat (recall). This keeps read vs. action explicit at the call site and avoids string sniffing.

// Create affordance now uses the action-routing handler.

Add the prop to TasksSectionImpl / TasksSectionBody signatures (lines 242, 250) and forward it through the {(isOpen) => …} render-prop. In page.tsx, pass onInjectAction={injectExecute} to <TasksSection> (the call site near line 104). Leave the other sections untouched — none of them currently inject actions.

Approach B (alternative, document only if chosen). Keep a single handler but make injectRecall's consumers tag the create string and have handleChatInject upgrade known create-prompts to execute. Rejected as default: it reintroduces string-matching coupling between the panel copy and the router. Record the choice in the PR description.

Change 4 — Carry real timestamps; remove the dead per-message attachments field

File: hub/app/page.tsx — sendToApi wire payload (lines 537–547).

Rationale. The mapper overwrites each message's timestamp with "now," collapsing real send times, and never carries per-message attachments (only the top-level field is sent). The server reads only role/content + top-level attachments, so this is currently harmless — but the rewritten timestamp is actively misleading and the implied per-message attachment support is dead. Carry the real timestamp (falling back to now only when absent) and drop the misleading intent by adding a short comment that per-message attachments are intentionally not on the wire.

import { describe, it, expect } from 'vitest'
import { shouldRouteThroughSend } from '@/app/lib/inject-routing' // small extracted helper

describe('panel inject routing', () => {
