Restore Google-document click + make chat failures diagnosable P0

Summary. Clicking a Google Drive document in the left panel currently surfaces the opaque message "Something went wrong on my end." in chat. The root cause is two compounding gaps: (1) the chat API route (hub/app/api/chat/route.ts) never wraps its handler body in a try/catch that returns a JSON Response, so any throw from getServerSession / getToken (secret rotation, corrupt cookie, JWT decode failure) becomes an opaque Next.js framework 500 with no JSON body and no structured log; and (2) the client (hub/app/page.tsx sendToApi) discards the server's JSON error/details on !res.ok and collapses every non-abort failure into the same generic string, so the operator sees nothing diagnosable and the user gets a dead end. This plan wraps the route in a Response-returning try/catch, surfaces the server's real details/error on the client (with a 401 vs 5xx branch), and removes two document-path latency/hang hazards (an unbounded extra Vertex call and two Drive fetch calls with no abort timeout). It also pins down two non-crashing checks (OAuth Drive scope; Vertex graceful-null behavior) so a coding agent can execute end to end without further context.

Why this matters

  • It is the actively-reported P0 bug. Drive-document attachments are the primary "left panel" interaction and they currently fail visibly with a non-actionable message.
  • It is currently undebuggable. When auth/JWT throws before streaming begins, Next.js returns a framework 500 with no JSON body and the route logs nothing structured — there is no log.error on that path. Operators staring at Cloud Run logs see only a generic stack, not a Hub-scoped error event.
  • The client hides the one useful signal. The server does emit JSON errors for the cases it handles (401 Unauthorized, 400 Invalid JSON / Messages array). The client throws those away at if (!res.ok) throw new Error(`API ${res.status}`) and never reads the body, so a recoverable "session expired, sign in again" is indistinguishable from a true 500.
  • Latency/hang risk on exactly this path. The document branch issues an extra, sequential searchSemanticBrain(...) after the main search pipeline already resolved. It is not wrapped in withTimeout, and its internal service-account token-exchange fetch has no abort timeout, so a slow Vertex/token endpoint can push the request toward the client's 45s abort — which then renders as the timeout message, masking the real cause.

Implementation

F1 — Wrap the POST handler in a Response-returning try/catch

File: hub/app/api/chat/route.ts

The cleanest diff is to extract the existing handler body into an inner async function (handleChat) and call it inside a single try/catch. The inner function returns the existing new Response(stream, …) (or the early-return JSON responses), and the catch logs a structured error and returns JSON 500. This guards both getServerSession (L160) and getToken (L193), plus any other synchronous throw before streaming starts. Note: errors that occur inside the stream's start() are already handled by the existing try/catch at L424–461 (they emit an SSE error event), so this wrapper specifically covers the pre-stream phase.

Current handler signature and the two unguarded awaits:

  // ... ~300 lines ... including:

  // ...

      'Content-Type': 'text/event-stream',

Refactor: rename the existing export async function POST(req: NextRequest) to a private async function handleChat(req: NextRequest): Promise<Response> (keep the entire body verbatim — including all early NextResponse.json returns and the final new Response(stream, …)), then add a thin exported POST wrapper:

async function handleChat(req: NextRequest): Promise<Response> {
  // Auth check
  const session = await getServerSession(authOptions)
  if (!session?.user) {
    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
  }

  // ... ENTIRE existing handler body, UNCHANGED ...

  return new Response(stream, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
      'Connection': 'keep-alive',
    },
  })
}

export async function POST(req: NextRequest) {
  try {
    return await handleChat(req)
  } catch (err) {
    const details = err instanceof Error ? err.message : 'Unknown error'
    log.error({ err }, 'Chat request failed before streaming started')
    return NextResponse.json(
      { error: 'Chat request failed', details },
      { status: 500 },
    )
  }
}

Rationale. Any throw from NextAuth session resolution or JWT decode (the exact failure mode behind the opaque 500) now produces a structured log.error event in Cloud Run and a JSON body the client can read. Extracting the body rather than indenting ~300 lines keeps the diff reviewable. log is already imported (const log = createLogger('chat'), L20) and NextResponse is already imported (L1).

F2 — Surface the server's real error on the client; branch on status

File: hub/app/page.tsx

Replace the body-discarding throw (L466) and the all-or-nothing catch (L529–539). Read the JSON error body on !res.ok, attach status to the thrown Error, and branch in the catch: 401 → "session expired, sign in again"; 5xx → generic message but keep logging the server details. Keep the existing AbortError (timeout) branch exactly.

      if (!res.ok) throw new Error(`API ${res.status}`)
      if (!res.ok) {
        // Surface the server's structured error instead of discarding it.
        let serverDetail = ''
        try {
          const errBody = await res.json()
          serverDetail = errBody?.details || errBody?.error || ''
        } catch {
          // non-JSON body (e.g. an opaque framework 500) — leave serverDetail empty
        }
        const apiErr = new Error(serverDetail || `API ${res.status}`) as Error & { status?: number }
        apiErr.status = res.status
        throw apiErr
      }

And the catch block:

    } catch (err) {

      const status = (err as { status?: number } | undefined)?.status

Rationale. A 401 (expired/missing session — common after secret rotation or a stale tab) now tells the user to re-auth instead of looking like a server crash. Genuine 5xx still shows a friendly generic message, but the real server details are now in the browser console for support. The AbortError/45s-timeout path is preserved verbatim. The thrown Error carries status so the catch can branch without re-reading the response.

F5 — Reveal a missing/expired Google token in the document fallback

File: hub/app/api/chat/route.ts

When the document branch reaches the resolvedParts.push(...) but neither Vertex nor Drive produced text, the cause is frequently a falsy accessToken (no/expired Google session). The current generic message hides that. Compute a clearer note and add a server log when the token is the reason.

          // Fallback: direct Drive API export
          if (!docText && accessToken) {
            docText = await fetchDriveDocContent(accessToken, att.fileId, att.mimeType)
          }

          resolvedParts.push(
            `### Attached Document: "${att.label}"\n\n${docText ?? '[Unable to retrieve document content]'}`
          )
          // Fallback: direct Drive API export
          if (!docText && accessToken) {
            docText = await fetchDriveDocContent(accessToken, att.fileId, att.mimeType)
          }

          if (!docText && !accessToken) {
            log.warn({ label: att.label, fileId: att.fileId }, 'Document attachment unresolved: no Google access token')
          }

          const docFallback = !accessToken
            ? '[Unable to retrieve document content: your Google session has no valid access token (it may be missing or expired). Ask the user to sign out and sign back in to re-grant Google Drive access.]'
            : '[Unable to retrieve document content]'

          resolvedParts.push(
            `### Attached Document: "${att.label}"\n\n${docText ?? docFallback}`
          )

Rationale. The model now receives an accurate, actionable explanation (re-auth) instead of a vague failure, and the operator gets a log.warn pinpointing the missing token. This is the most common real cause of a failed Drive-document click after a token expiry.

  4. F6 anytime. Verification step; only becomes an edit if the scope is missing.
  5. F7 never edited. Context note.

Rollback

  • All changes are localized and additive; revert per file via git revert / git checkout of the touched paths.
  • F1 is the highest-leverage and lowest-risk change (it only adds an outer wrapper); reverting it restores the prior opaque-500 behavior but breaks nothing else. The extracted handleChat body is byte-for-byte the previous handler, so a revert is a clean rename back to POST.
  • F2 revert restores the single generic message; the server still emits JSON errors (harmless if unread).
  • F3/F4 reverts remove the timeouts and reintroduce the hang risk only under slow upstreams — no correctness change.
  • F5 revert restores the generic fallback string; no behavioral risk.
  • If the new tests prove flaky in CI (e.g. module-mocking friction), they can be skipped independently of the source changes — the source fixes do not depend on the tests.
