Left-Panel Audit 08 — Accessibility completion: modals, tabs, and KPI cards P2

Target file (all changes): hub/app/components/LeftPanelSections.tsx
New file: hub/app/hooks/useModalA11y.ts
Repo: /home/user/hub-overlay (app under hub/)

Summary

Plan 06 (PR #19) hardened the mobile drawer shell — it turned the left-panel <aside> into a viewport-conditional dialog with a Tab focus trap, Escape-to-close, focus move-in, focus restoration, and body scroll-lock (all in hub/app/page.tsx). It did not touch the in-panel widgets. This piece closes the remaining ARIA gaps inside the left panel itself:

  • Two modals — the calendar create modal (CalendarEventModal) and the delete-confirm alertdialog — declare role="dialog"/aria-modal but have no Escape handler, no focus trap, and no focus restoration. We add a small shared hook (useModalA11y) and apply it to both.
  • Three faux-ARIA widget patterns — Tasks list tabs, Documents filter tabs, and the calendar week strip listbox — claim composite-widget roles (tablist/tab, listbox/option) but ship none of the required keyboard model (arrow-key roving focus, aria-controls→panel). We add a tiny roving-tabindex helper and wire arrow keys, and connect the tab strips to their panels.
  • KPI cards nest three competing accessible names (button label + trend div label + AnimatedNumber's own label). We make the inner content decorative so the button's single label is announced.
  • Two buttons mis-typed as role="listitem" (the artifact button and DocumentRow), which overrides the implicit button role. We wrap each button in a <div role="listitem"> instead.

No source behavior changes beyond accessibility; no API or data-layer edits. This document only writes the plan — do not modify source while authoring it.

Why this matters

  • Keyboard users get trapped or lost. A dialog with aria-modal="true" tells assistive tech "everything else is inert," yet Tab currently walks out of the modal into the page behind it, and there is no way to dismiss with Escape. On close, focus is dropped to <body>, forcing the user to Tab from the top of the document. This is a WCAG 2.1 2.1.2 (No Keyboard Trap) / 2.4.3 (Focus Order) failure.
  • Composite-widget roles promise a keyboard contract we don't honor. role="tablist" and role="listbox" make screen readers announce "tab list" / "list box" and lead users to expect arrow-key navigation between options with a single Tab stop. We instead render N independent Tab stops and no arrow handling — confusing and a 4.1.2 (Name, Role, Value) mismatch.
  • Redundant nested labels create noisy, duplicated announcements. A KPI card currently announces its label/value/trend up to three times (button label, then the trend div's label, then the animated number's label) because each carries its own aria-label.
  • Role overrides silently break semantics. <button role="listitem"> discards the button role; the element is announced as a static list item, so screen-reader users may not realize it is actionable.

Change A — Shared modal-a11y hook

File: new hub/app/hooks/useModalA11y.ts

Create one hook that both modals consume. It mirrors the drawer pattern already proven in page.tsx (focusable-selector query, first/last wrap, document.activeElement capture/restore), packaged for an always-mounted-on-open modal. The hook takes a ref to the dialog element and an onClose callback; it (1) captures the trigger element on mount, (2) moves focus into the dialog on the next animation frame, (3) handles Escape to close, (4) traps Tab within the dialog, and (5) restores focus to the trigger on unmount.

// hub/app/hooks/useModalA11y.ts
'use client'

import { useEffect, RefObject } from 'react'

const FOCUSABLE =
  'a[href], button:not([disabled]), input:not([disabled]), select:not([disabled]), ' +
  'textarea:not([disabled]), [tabindex]:not([tabindex="-1"])'

/**
 * Accessibility behavior for an always-rendered-when-open modal dialog:
 *  - captures the trigger element and restores focus to it on close/unmount
 *  - moves focus into the dialog on open (first focusable, or the dialog itself)
 *  - Escape closes
 *  - Tab is trapped within the dialog (wraps first <-> last)
 *
 * Mount this hook in a component that is only rendered while the dialog is open
 * (both call sites already gate rendering behind `showCreateModal` / `deleteConfirm`).
 */
export function useModalA11y(
  dialogRef: RefObject,
  onClose: () => void,
) {
  useEffect(() => {
    const dialog = dialogRef.current
    if (!dialog) return

    const trigger = (document.activeElement as HTMLElement) ?? null

    // Move focus in on the next frame (after the open transition applies).
    const raf = requestAnimationFrame(() => {
      const focusable = dialog.querySelectorAll(FOCUSABLE)
      ;(focusable[0] ?? dialog).focus()
    })

    const onKeyDown = (e: KeyboardEvent) => {
      if (e.key === 'Escape') {
        e.preventDefault()
        onClose()
        return
      }
      if (e.key !== 'Tab') return
      const focusable = dialog.querySelectorAll(FOCUSABLE)
      if (focusable.length === 0) return
      const first = focusable[0]
      const last = focusable[focusable.length - 1]
      if (e.shiftKey && document.activeElement === first) {
        e.preventDefault(); last.focus()
      } else if (!e.shiftKey && document.activeElement === last) {
        e.preventDefault(); first.focus()
      }
    }

    document.addEventListener('keydown', onKeyDown)
    return () => {
      cancelAnimationFrame(raf)
      document.removeEventListener('keydown', onKeyDown)
      // Restore focus to the element that opened the dialog.
      trigger?.focus()
    }
  // onClose is stable per render of the gated component; including it is safe.
  }, [dialogRef, onClose])
}

Rationale: One hook, two call sites, identical guarantees. Listening on document (not the dialog) for keydown means Escape works even when focus has not yet entered the dialog. The cleanup runs on unmount — which is exactly when each modal closes, because both call sites conditionally render the modal. We make the dialog itself focusable as a fallback target (see Change B) so focus always lands inside.

Change D — Roving-tabindex + arrow-key helper

File: hub/app/components/LeftPanelSections.tsx

Add one small module-scope helper used by all three composite widgets. It implements Left/Right/Home/End roving focus over sibling option/tab buttons within a container, moving DOM focus and (optionally) invoking a select callback. Place it in the utilities region near the bottom (after 1267) or just above the first consumer — module scope, allocated once.

/**
 * Roving keyboard navigation for a horizontal composite widget (tablist / listbox).
 * Wire to the container's onKeyDown. `selectors` targets the option elements.
 * Moves focus with ArrowLeft/Right + Home/End and calls onSelect with the new index.
 */
function handleRovingKeydown(
  e: React.KeyboardEvent<HTMLElement>,
  optionSelector: string,
  onSelect: (index: number) => void,
) {
  const keys = ['ArrowLeft', 'ArrowRight', 'Home', 'End']
  if (!keys.includes(e.key)) return
  const container = e.currentTarget
  const options = Array.from(container.querySelectorAll<HTMLElement>(optionSelector))
  if (options.length === 0) return
  const current = options.indexOf(document.activeElement as HTMLElement)
  let next = current
  if (e.key === 'ArrowRight') next = current < 0 ? 0 : (current + 1) % options.length
  else if (e.key === 'ArrowLeft') next = current <= 0 ? options.length - 1 : current - 1
  else if (e.key === 'Home') next = 0
  else if (e.key === 'End') next = options.length - 1
  e.preventDefault()
  options[next]?.focus()
  onSelect(next)
}

Rationale: One implementation satisfies the APG keyboard model for both tablist (automatic activation: focusing a tab selects it) and listbox (selection follows focus). Roving tabindex (one option at tabIndex={0}, the rest -1) is set per-widget below so the whole strip is a single Tab stop.

Manual keyboard-only checks (no mouse)

  • Create modal trap + Escape + restore: Tab to the "+ Event" button and press Enter. Focus should land inside the modal. Tab repeatedly — focus must cycle within the modal (Title → … → Cancel → Save → back to Title) and never reach the page behind. Shift+Tab wraps backward. Press Escape — modal closes and focus returns to the "+ Event" button.
  • Delete dialog: Tab to an event's trash button, activate it. Focus enters the alertdialog; Tab is trapped; Escape closes and returns focus to the trash button. Confirm Delete still works and that an error keeps the dialog open.
  • Documents filter tabs: Tab once to reach the tablist (a single stop). Press Right/Left arrows — the active tab moves and content switches; Home/End jump to first/last. Tab again moves into the tabpanel, not to the next tab.
  • Tasks list tabs: (requires >1 task list) same arrow-key behavior.
  • Week strip: Tab to the strip (single stop on the selected/today cell). Left/Right/Home/End move the selected day and update the day-detail list below.
  • KPI cards (screen reader): With VoiceOver/NVDA, focus a KPI card — it announces exactly one string (e.g. "Revenue: 42, trend +5%, button"), not the number or trend a second time.
  • List semantics (screen reader): Artifact rows and document rows announce as "button" within a "list", not as static list items.

Acceptance criteria

  • npx tsc --noEmit and npx vitest run both pass.
  • Both modals (create + delete): focus enters on open, Tab is trapped, Escape closes, focus returns to the triggering control on close.
  • All three composite widgets (Documents tabs, Tasks tabs, week strip) are a single Tab stop with working Arrow/Home/End roving focus; tab strips expose aria-controls→a role="tabpanel" labeled by the active tab.
  • Each KPI card exposes exactly one accessible name (the button's aria-label); the value and trend subtrees are aria-hidden.
  • No element uses <button role="listitem">; the artifact button and DocumentRow are wrapped in <div role="listitem">. Parent role="list" containers have only listitem children.
  • No visual regression in the left panel; no changes to page.tsx drawer behavior.
