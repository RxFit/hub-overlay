Plan 05 — Polling Cost & Data-Layer Consolidation P1

Summary. The left panel over-fetches in three structurally distinct ways: (1) CollapsibleSection only toggles CSS visibility, so collapsed KPI / Tasks / Calendar / Documents sections keep their SWR hooks mounted and keep polling on every interval; (2) the heaviest endpoint, /api/kpis, is subscribed twice (in HubPage and again inside KPISection) with no dedupingInterval and revalidateOnFocus:true, and overlaps with /api/projects; and (3) chat unread counts run a raw setInterval that bypasses SWR entirely, re-fetching messages that useMessages already caches, with a stale-closure footgun on spaces. This plan gates polling on section open-state, lifts and dedupes the KPI subscription, routes unread counts through the SWR cache (or a single batched endpoint), and standardizes SWR config across the data hooks.

All file paths are relative to the repo root /home/user/hub-overlay; the app lives under hub/.

Why this matters

  • Wasted quota & rate-limit pressure. Google Tasks/Calendar/Drive/Chat and Paperclip KPI endpoints all poll continuously even when their section is collapsed or off-screen. Tasks alone fire an N+1 fan-out (list fetch + one fetch per task list) every 30s regardless of visibility.
  • Duplicate subscriptions. /api/kpis has two live SWR subscriptions. SWR dedupes the network request only inside its (currently unset) dedupingInterval window; with revalidateOnFocus:true and no deduping window, focus events and interval drift can produce redundant fetches and double re-renders.
  • Overlapping sources of truth. /api/kpis (via useKPIData) and /api/projects (via useProjects, used in BrandedHeader) both return project/health data and both poll at 60s with revalidateOnFocus, doubling the project-health request volume.
  • SWR-bypass. useUnreadCounts hand-rolls setInterval(…,60_000) and manual fetch calls against the same /api/google/chat/messages URLs SWR already owns — no dedupe, no cache reuse, and a stale-closure bug where the effect depends on [spaceIds] but its callback closes over the full spaces array.
  • Config drift. useProjects/useCompanies set dedupingInterval:30_000; useKPIData and the useHubData hooks do not. Inconsistent revalidateOnFocus and retry settings make caching behavior unpredictable.

Change 2 — Dedupe the Tasks N+1 cadence

File: hub/app/hooks/useHubData.ts (useTasks, lines 82–137)

Both SWR calls poll at 30s: the task-lists fetch (line 90) and the per-list aggregate fan-out (line 124). The fan-out re-fetches every list every 30s.

// …
// per-list aggregate — raise to 60s and gate on open-state

Change 5 — Route chat unread through SWR (kill the raw setInterval)

File: hub/app/hooks/useGoogleChat.ts (useUnreadCounts, lines 229–297)

The current implementation runs setInterval(computeUnreads, 60_000) (line 288) inside an effect whose dependency array is [spaceIds] (line 294), while computeUnreads closes over the full spaces array (lines 246–251) — a stale-closure footgun if spaces changes content without changing the sorted-id string. Each tick manually fetches /api/google/chat/readstate and /api/google/chat/messages?…&pageSize=50 (lines 253, 261), duplicating the exact messages URL useMessages already caches (line 117/120).

Preferred fix (one batched endpoint). Add a server route GET /api/google/chat/unread that accepts the space-id set and returns { unread: Record<string,number>, total: number }, then back the hook with a single SWR subscription:

// useGoogleChat.ts — useUnreadCounts via SWR
export function useUnreadCounts(spaces: ChatSpace[]) {
  const spaceIds = spaces.map(s => s.name).sort()
  const key = spaceIds.length
    ? `/api/google/chat/unread?spaceIds=${encodeURIComponent(spaceIds.join(','))}`
    : null
  const { data } = useSWR<{ unread: Record<string, number>; total: number }>(
    key, fetcher,
    { refreshInterval: 60_000, revalidateOnFocus: false, dedupingInterval: 30_000 }
  )
  const unreadMap = new Map(Object.entries(data?.unread ?? {}))
  return { unreadMap, totalUnread: data?.total ?? 0 }
}

Fallback fix (no new endpoint). If adding a route is out of scope for this PR, keep the per-space readstate fetch but read message data from the SWR cache instead of re-fetching it, and fix the closure: depend the effect on the actual spaces identity (or a content hash) and read spaces from a ref so the interval callback never goes stale. At minimum, replace the manual fetch(.../messages…) (line 261) with useSWRConfig().cache.get(key) for the same key useMessages uses (line 117), avoiding the duplicate network call. The batched endpoint is strongly preferred because it also collapses N readstate requests into one.

Both consumers — page.tsx line 253 and GoogleChatPanel.tsx line 797 — call useUnreadCounts(spaces) and read { unreadMap, totalUnread }; the return shape is unchanged, so no call-site edits are required.

Rationale. The current loop is the single worst offender: N×2 un-deduped fetches per minute, immune to SWR caching, plus a latent staleness bug. Moving it under SWR gives dedupe, focus control, and cache reuse for free; the batched endpoint additionally removes the per-space fan-out entirely.

Change 6 — Standardize SWR config

Files: hub/app/hooks/useKPIData.ts, hub/app/hooks/useHubData.ts (and verify useGoogleChat.ts)

Reconcile config against the already-consistent useProjects.ts (lines 27–31) / useCompanies.ts (lines 26–30), which both use refreshInterval:60_000, revalidateOnFocus:true, dedupingInterval:30_000. Target conventions for left-panel polling hooks:

  • dedupingInterval: 30_000 on every left-panel hook (currently missing from useKPIData and all useHubData hooks).
  • revalidateOnFocus: keep false for the high-frequency Google hooks (Tasks/Calendar/Drive already do) and set useKPIData to false (Change 3); leave the slow Paperclip/companies hooks as-is.
  • Gate refreshInterval on isOpen (Change 1) consistently.
  • Leave useBusinessManager (5-min cadence, retry config, lines 48–54) and useSpaceMembers (5-min, line 204) untouched — their cadence is intentional.

Rationale. A single, predictable caching contract makes the dedupe windows actually line up across hooks that hit related endpoints, and prevents future drift.

Acceptance criteria

  • Collapsing any of KPI / Tasks / Calendar / Documents stops that section's polling (verified in Network); re-opening resumes it and shows cached data immediately.
  • /api/kpis has exactly one live SWR subscription; only one request fires per refresh cycle; useKPIData has dedupingInterval:30_000 and revalidateOnFocus:false.
  • KPISection receives kpis/isLoading as props (no internal useKPIData call).
  • The Tasks per-list fan-out polls no faster than 60s; the task-lists fetch polls no faster than 5min.
  • useUnreadCounts contains no raw setInterval and issues no duplicate /api/google/chat/messages fetches; the return shape { unreadMap, totalUnread } is unchanged for both consumers.
  • Project health is fetched from a single authoritative source, or the residual overlap is explicitly documented as accepted.
  • All left-panel polling hooks carry dedupingInterval:30_000 and a reconciled revalidateOnFocus.
  • npx tsc --noEmit and npx vitest run pass.

Rollback

  • Each change is independently revertable. To roll back gating (C1/C2), restore the unconditional refreshInterval literals and the plain children: ReactNode signature on CollapsibleSection.
  • To roll back the KPI lift (C3/C4), restore useKPIData(activeProject) inside KPISection (line 968) and useProjects() inside BrandedHeader (line 36); remove the props threading in page.tsx. Behavior returns to double-subscription but functional.
  • To roll back the unread rewrite (C5), restore the setInterval-based useUnreadCounts; the return shape is unchanged so no consumer edits are needed. If the batched route was added, it can be left in place unused or deleted.
  • No database/schema changes; rollback is purely code-level. Revert by reverting the PR.
