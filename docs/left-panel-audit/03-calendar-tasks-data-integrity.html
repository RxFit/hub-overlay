Calendar & Tasks Data Integrity P0

Piece: Calendar & Tasks data integrity. Newly created calendar events silently lose the user-entered location and land at the wrong hour (the modal sends naive local datetime strings with no time zone, so Google interprets them against the calendar's default zone). Independently, task due dates render nonsensically — a task due tomorrow shows "just now" because the formatter only ever computes elapsed past time. A date off-by-one bug compounds both for the user's Central (negative UTC offset) time zone.

Repo: /home/user/hub-overlay (app under hub/). All paths below are absolute.

Why this matters

  • Wrong-time events are a data-corruption bug, not a cosmetic one. A user in Austin (US Central) creating a 9:00 AM event sends the string 2026-06-24T09:00:00 with no offset. Google's events.insert treats a zone-less dateTime as the calendar's default time zone. If that default differs from the user's local zone (common — calendars are often left on a server/account default), the event lands at the wrong hour. The user has no signal that anything went wrong until they miss the meeting.
  • Location is collected, validated, and then dropped. The modal has a Location input; the request body includes it; the Zod schema explicitly permits it — but createCalendarEvent never copies it into the Google payload. Every event created through the panel loses its address / Meet link. Silent data loss is worse than a visible failure.
  • Due dates that say "just now" destroy trust in the panel. A future due date routed through a past-only "X ago" formatter collapses to "just now", making the task list look broken and actively misleading.
  • The user is in Austin (Central, UTC−5/−6). Every off-by-one and zone bug here is guaranteed to reproduce for this user, not just a theoretical edge case.

export async function createCalendarEvent(
  accessToken: string,
  event: {
    summary: string
    description?: string
    start: string   // ISO datetime or date
    end: string     // ISO datetime or date
    attendees?: string[]  // email addresses
    location?: string
    timeZone?: string  // IANA tz, e.g. "America/Chicago"; required for correct timed events
    calendarId?: string
  }
): Promise<GoogleCalendarEvent> {
  const calId = encodeURIComponent(event.calendarId ?? 'primary')
  const isAllDay = event.start.length === 10  // "2026-05-30" vs "2026-05-30T10:00:00"

  // For timed events, attach the caller's IANA time zone so Google anchors the
  // naive local datetime to the right offset instead of the calendar default.
  const startField = isAllDay
    ? { date: event.start }
    : { dateTime: event.start, ...(event.timeZone ? { timeZone: event.timeZone } : {}) }
  const endField = isAllDay
    ? { date: event.end }
    : { dateTime: event.end, ...(event.timeZone ? { timeZone: event.timeZone } : {}) }

  const body: Record<string, unknown> = {
    summary: event.summary,
    description: event.description,
    start: startField,
    end: endField,
  }

  if (event.location) body.location = event.location

  if (event.attendees?.length) {
    body.attendees = event.attendees.map(email => ({ email }))
  }

Rationale: location is now copied into the Google payload, ending the silent data loss. timeZone is attached per RFC 3339 only to timed events; all-day events stay as { date } with no zone (Google rejects a timeZone on a date field). When timeZone is absent the behaviour is unchanged, so the change is backward-compatible for any other caller.

4. T-P1-3 + T-P2-1 — A due-date formatter that handles future and overdue

File: /home/user/hub-overlay/hub/lib/panel-inject.ts

Google Tasks due is a date-only timestamp at UTC midnight (e.g. 2026-06-25T00:00:00.000Z). Two bugs stack: (a) formatRelativeDate is past-only, so a future due date returns "just now"; (b) formatting that UTC-midnight value in local time shifts the day backward for Central users. Add a dedicated formatDueDate that parses the date portion in local terms and computes a signed day delta.

4a. Add the formatter (place it next to formatShortDate / formatRelativeDate, after line 85):

/**
 * Format a Google Tasks `due` value (date-only, UTC midnight) for display.
 * Parses the DATE portion in local terms so the day doesn't shift for
 * negative-offset users, and reports future deltas + overdue — unlike
 * formatRelativeDate, which is past-only and would say "just now" for a
 * task due tomorrow.
 */
export function formatDueDate(isoString: string): string {
  try {
    // Take the YYYY-MM-DD prefix and build a LOCAL midnight date so the
    // calendar day matches what the user sees, not the UTC instant.
    const [y, m, d] = isoString.slice(0, 10).split('-').map(Number)
    if (!y || !m || !d) return isoString
    const due = new Date(y, m - 1, d)

    const now = new Date()
    const today = new Date(now.getFullYear(), now.getMonth(), now.getDate())
    const diffDays = Math.round((due.getTime() - today.getTime()) / 86_400_000)

    if (diffDays === 0) return 'Today'
    if (diffDays === 1) return 'Tomorrow'
    if (diffDays === -1) return 'Yesterday (overdue)'
    if (diffDays < 0) return `${-diffDays}d overdue`
    if (diffDays < 7) return `in ${diffDays}d`
    return due.toLocaleDateString([], { month: 'short', day: 'numeric' })
  } catch {
    return isoString
  }
}

Dependencies & sequencing

  1. Change 1 (google.ts) first — establishes the new param contract that the route and tests depend on.
  2. Change 2 (zod-schemas.ts) next — without it, Zod strips timeZone from the request before it reaches change 1, so the wrong-hour fix is silently inert. These two must ship together. No route edit is needed (route.ts:95 forwards parsed.data as-is).
  3. Change 3 (modal) after 1–2 — the client must send timeZone for the end-to-end fix; sending it before the schema accepts it is harmless (stripped) but pointless.
  4. Change 4 (formatDueDate) is independent of the calendar fixes and can land in parallel; the panel-inject.ts helper must exist before the LeftPanelSections.tsx import/usage edits compile.
  5. Change 5 (summary?) is independent but should land with the others so the single tsc pass catches all newly-surfaced optional-access sites at once.
  6. Run tsc --noEmit only after the type change (5a) and all consumer edits are in place, so the compiler validates the full set.

No new packages, env vars, migrations, or API-scope changes. Intl.DateTimeFormat().resolvedOptions().timeZone is universally available in supported browsers; the || undefined guard degrades gracefully to prior behaviour if it ever returns empty.

Rollback

  • Each change is a self-contained, additive edit; revert per-file via git with no data migration required.
  • The schema field and the createCalendarEvent params are optional, so reverting the client (change 3) while keeping the server changes is safe — the server simply receives no timeZone/location and behaves as before.
  • Reverting change 4 restores formatRelativeDate for due dates (re-introducing the "just now" bug) but breaks nothing else; formatDueDate is purely additive and unused elsewhere.
  • Reverting change 5a (back to summary: string) is safe only if the corresponding fallback edits (5b) are also reverted; otherwise the fallbacks remain harmless dead-defaults. Prefer reverting 5a + 5b together.
  • No persisted state is altered by these changes, so rollback cannot corrupt existing events or tasks; previously-created (wrong-time / location-less) events are not retroactively modified and would need manual correction in Google Calendar.
