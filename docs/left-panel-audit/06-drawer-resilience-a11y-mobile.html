Left-panel resilience, accessibility & mobile P0 P1

Scope: the Left ("Context Layer") panel and its mobile drawer behaviour. Repo: /home/user/hub-overlay, app under hub/. Primary files: hub/app/page.tsx, hub/app/components/LeftPanelSections.tsx, hub/app/hooks/useSwipePanels.ts.

Summary

The left panel has two structural defects that justify P0 treatment. First, there is no React Error Boundary anywhere in the app — LeftPanel renders its four data sections (KPIs, Calendar, Tasks, Documents) as plain siblings, so a single render-time throw in any one of them propagates up to HubPage and blanks the entire application rather than degrading one section. Second, the mobile drawer is a modal overlay with a backdrop but lacks the accessibility contract the app already applies to its own CalendarEventModal: no role="dialog"/aria-modal, no focus trap, no focus move-in, no focus restoration, no body-scroll-lock, and no Escape-to-close. Several P1/P2 items (memoization, heading semantics, duplicate landmarks, keyboard-operable task rows, swipe-style desync) round out the work.

This plan adds a lightweight class-based ErrorBoundary, brings the drawer up to the modal-dialog bar, locks body scroll while a panel is open, wires Escape-to-close, memoizes the panel and its sections so chat keystrokes stop re-rendering them, and fixes the heading/landmark/keyboard a11y nits and the swipe edge cases.

Why this matters

  • One bad section should not blank the app. Today a thrown error in KPISection, CalendarSection, TasksSection, or DocumentsSection takes down HubPage — the user loses chat, the right panel, everything. An error boundary contains the blast radius to the offending section, which already has a graceful SectionMessage type="error" idiom for data-load failures.
  • The drawer is less accessible than the app's own modal. CalendarEventModal (in LeftPanelSections.tsx) correctly sets role="dialog" aria-modal="true". The mobile left drawer — which is functionally a modal overlay — does none of this. Keyboard and screen-reader users can tab into content behind the backdrop, can't Escape out, and lose their place on close.
  • Background scroll bleeds through. With no body scroll-lock, opening a panel lets the page behind the backdrop scroll, a classic mobile-overlay defect.
  • Every chat keystroke re-renders the whole panel. The inject handler prop (injectRecall) is already a stable useCallback, but the panel and sections are unmemoized, so they re-render on every HubPage state change (e.g. typing in the chat box). Memoizing lets the stable prop actually buy a skipped render.

Change 1 — Lightweight class-based ErrorBoundary, wrapping the panel content (Finding 1, P0)

File: hub/app/components/LeftPanelSections.tsx (define + export the boundary here, where the private SectionMessage fallback lives) and hub/app/page.tsx (consume it).

Add a small class component. Place it near the top of LeftPanelSections.tsx, just after the existing SectionMessage definition (line 56). It must be a class because error boundaries require getDerivedStateFromError/componentDidCatch, which have no hooks equivalent. Import Component from React (extend the existing line 3 import).

// LeftPanelSections.tsx — add immediately after SectionMessage (after line 56)

/* ══════════════════════════════════════════════════════════════════════════════
   ERROR BOUNDARY — contains a render throw to a single section
   ══════════════════════════════════════════════════════════════════════════════ */

export class SectionErrorBoundary extends Component<
  { label?: string; children: ReactNode },
  { hasError: boolean }
> {
  state = { hasError: false }

  static getDerivedStateFromError(): { hasError: boolean } {
    return { hasError: true }
  }

  componentDidCatch(error: Error, info: ErrorInfo) {
    // Surface in dev / wire to telemetry later; do not rethrow.
    console.error('[SectionErrorBoundary]', this.props.label ?? '', error, info)
  }

  render() {
    if (this.state.hasError) {
      return (
        <SectionMessage
          message={`Unable to display ${this.props.label ?? 'this section'} — try refreshing`}
          type="error"
        />
      )
    }
    return this.props.children
  }
}

useEffect(() => {

// Focus management for the mobile left drawer
useEffect(() => {
  if (!(mobileLeftOpen && isMobileViewport)) return
  const panel = leftPanelRef.current
  if (!panel) return

  leftOpenerRef.current = (document.activeElement as HTMLElement) ?? null
  // Move focus in (next frame so the open transition/visibility has applied)
  const raf = requestAnimationFrame(() => leftCloseBtnRef.current?.focus())

  const onKeyDown = (e: KeyboardEvent) => {
    if (e.key !== 'Tab') return
    const focusable = panel.querySelectorAll<HTMLElement>(
      'a[href], button:not([disabled]), input:not([disabled]), select:not([disabled]), textarea:not([disabled]), [tabindex]:not([tabindex="-1"])'
    )
    if (focusable.length === 0) return
    const first = focusable[0]
    const last = focusable[focusable.length - 1]
    if (e.shiftKey && document.activeElement === first) {
      e.preventDefault(); last.focus()
    } else if (!e.shiftKey && document.activeElement === last) {
      e.preventDefault(); first.focus()
    }
  }
  panel.addEventListener('keydown', onKeyDown)

  return () => {
    cancelAnimationFrame(raf)
    panel.removeEventListener('keydown', onKeyDown)
    // Restore focus to the opener (e.g. the command nav button)
    leftOpenerRef.current?.focus?.()
  }
}, [mobileLeftOpen, isMobileViewport, leftPanelRef])

Acceptance criteria

  • A render-time throw in any one left-panel section is contained to that section (error message shown) and never blanks HubPage.
  • The mobile left drawer exposes role="dialog" aria-modal="true" only when open on a mobile viewport; focus moves to the close button on open, is trapped within the drawer, and returns to the opener on close.
