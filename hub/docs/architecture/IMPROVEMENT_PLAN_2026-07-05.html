Architectural principles

Five rules the workstreams inherit

  1. Server is the only authority for consequence. Any client gate (interview score, Pre-Cog, role, rate) is UX; the write boundary must re-derive or re-verify it. The through-line of Wave 1.
  2. Verify before you fix. Both source documents proved partly stale against live code (reduced-motion already done; rate limiter already gone). Every security task opens with a code-truth check; "already done" is a valid, welcome outcome.
  3. Fence at the boundary, once. Untrusted text (email, Exa, fetched URLs, Drive docs, Paperclip titles) is wrapped in <untrusted_data> where it enters the prompt — one choke point, tested once. P8 already routes Gmail/Chat through fenceUntrusted; complete the coverage.
  4. Single source for config & scope. The hardcoded Paperclip URL, company IDs, and 'rxfit' literal collapse to one env-sourced module — the seam multi-tenancy reopens later. Keep it clean; don't build it. Do not collapse the intentional two-instance separation.
  5. Refactor only under a net. No touching the page.tsx / settings / globals.css monoliths until Playwright e2e runs in CI. #11 gates #12 — a prior useChatOrchestrator attempt was reverted (no remnant in code), exactly the risk the net removes.

Intent

Move every consequential gate to the write boundary, restore the lost request limiter, and close the confirmed authorization gaps. This is what makes "the AI can act" safe to ship — the true launch blocker.

Architecture

  • Recover the request limiter (#16). Re-implement the June-16 spec (sliding window, 15 req / 60s per email, in-memory Map + background sweep, 429 + Retry-After, 512KB body guard → 413) as lib/rate-limit.ts, applied at the top of /api/chat. Recovery, not design — the vault entry Backend_Hardening_H1_M5_C6.md is the reference. Cost + abuse protection on the most expensive path (each call fans out to Vertex/pgvector/Exa + a model stream).
  • Gate as a server-verified token (#1 / P0-2 remainder). The signed gateToken (minted by /api/chat/score-context) already gates the Paperclip issue path; the Google send routes don't check it. Generalize to a requireGate(req, intent) guard the AI-origin send routes call before executing. Verify first: the client already fails closed (finalScore = 0, not 80 — the audit's claim is stale) and lib/gateToken.ts exists; this is wiring the server check, not inventing the primitive.
  • Role → method → path matrix in the proxy (P0-1 / P1-6). Replace the ad-hoc allowlist in api/paperclip/[...path]/route.ts with a declarative table (staff = read + issue-create; admin = mutate/reassign/restart; superadmin = delete), covering the direct resource routes (/api/issues/:id, /api/agents/:id) the CTO audit flagged. Align delete_agent to superadmin; validate assigneeId/assigneeUserId server-side against the target company.
  • Complete the fence (P1-1). Route Exa snippets, fetched-URL text, Drive content, and attachments through the same fenceUntrusted Gmail/Chat use; unit-test that an "ignore previous instructions" payload lands inside the fence.
  • Auth resilience (P1-2) + strict Zod (P1-4). Drop accessToken in the JWT callback when token.error is set (one fix, every Google route); make paperclipFetch throw on list-endpoint schema failure instead of returning raw as T.

Verified-stale, do not re-fix: P0-2 "finalScore defaults to 80" (code is = 0), webhook token bypass (fail-closed), embeddings auth (Bearer). Confirm in the opening verify-PR, then cross off.

Architecture

  • Message kind field (#10 · Wave 1). Replace the content.includes('Interview complete!') cleanup — fragile at 5 sites in page.tsx, and a user message quoting the phrase corrupts state — with a typed kind discriminator. Correctness bug; do it before the extraction so the new hook is born clean.
