# The Deep Lane — Deep Research & Deep Think on the `agy` Engine

**Status:** design, in execution · **Written:** 2026-08-23
**Sits under:** `scripts/agy/README.md` (migration blueprint) — this doc is the first arc of the Phase 4 row.
**Follows:** `PHASE3_EXECUTION_PANEL_2026-08-22.md` (whose §7 names this lane's gaps as "Phase 4's real starting list").

---

## 1. Why these two tools don't fit the machinery the other tools use

Every existing Hub tool — Prioritization, Issue Tree (MECE), SCPR, Decision Memo, the
rest of the enterprise-ai suite — is a *prompt shaper*. Activating one loads its
`SKILL.md` into the system prompt of an ordinary chat turn
(`app/api/chat/route.ts:826-830`), the reply comes back inside the normal chat budget,
and `lib/parseToolArtifacts.ts` regex-scrapes it into panel cards. The tool is a lens
on a single synchronous turn.

Deep Research and Deep Think are a different species: **minutes-long, multi-step,
tool-using runs**. The chat path structurally cannot carry them, for two load-bearing
reasons:

- **The allotment attempt is clamped to 45–90 s.** `agyChatTimeoutMs()` caps every agy
  chat attempt at 90 s hard (`lib/agy-chat.ts:101-105`), because chat must never
  stall. A deep run needs 5–20 minutes.
- **Failure falls through to metered Gemini.** Correct for chat — chat must never
  break — but for a "deep" tool it is the worst outcome dressed as success: the user
  asks for depth, the allotment times out, and a shallow single-pass metered answer
  comes back *billed*. Both promises (depth, and agy's tokens) silently break.

So the design principle: **deep tools do not ride the chat lane at all.**

## 2. The design in one paragraph

A deep tool run is a **briefed, durable, asynchronous agy run**: the user confirms a
short brief in the tool panel; the Hub writes a durable `tool_runs` row and enqueues a
`work_item` dispatch job; the desktop worker executes it with `agy -p` on the
allotment — with agy's full desktop tool belt, since the gateway already passes
`--dangerously-skip-permissions` (`lib/agy.ts`) — heartbeating its lease for as long
as the run needs; the result lands back in `tool_runs` plus a `source: 'tool'` row in
the `ai_runs` ledger; the panel polls, renders the report, and offers
Save-to-artifacts and Insert-into-chat. This is Phase 4's "brief and verify an `agy`
run," shipped as two products instead of as plumbing.

Deep Research and Deep Think are the same machinery with different briefs: Research is
a tool-using run (web search, MCP servers on the desktop) that triangulates sources
into a cited report; Think is a no-tools run at `effort: 'high'` — an option the
worker wire format already carries (`lib/dispatch-worker.ts:59,178-179`) — through a
deliberation protocol: framings, strongest case each way, self-critique, conclusion.

## 3. The lane already exists — evidence

Phase 2.5 shipped a second dispatch kind that has never carried a job. Its policy was
written for exactly this shape of work (`lib/dispatch-store.ts` KIND_POLICY):

| Property | `chat_turn` (live) | `work_item` (dormant) |
|---|---|---|
| Priority | 0 | 100 |
| Attempts | 1 — at-most-once | 3 — at-least-once |
| Lease | 25 s | 180 s, renewed to now+180 s on every 30 s heartbeat (`heartbeatJob`) — a run lasts as long as its deadline |
| On lapsed lease | dead — turn already fell back | requeued while attempts remain |
| Queue cap | 3 active | 10 queued |
| Worker slots | `WORKER_CHAT_SLOTS` (1) | `WORKER_WORK_SLOTS` — defaults 0, deliberately, "pending exactly this panel work" (`lib/dispatch-worker.ts:17-18`) |

Slot pools are separate per kind (`lib/dispatch-worker.ts:319-325`), so a 20-minute
research run can never starve chat — and the 2026-08-19 concurrency test established
PARALLEL_OK for simultaneous runs on one token. Phase 3's §7 gap list — the enqueuer
hardcoded `kind: 'chat_turn'`, work slots default 0, `reapExpired()` never wrote a
ledger row, the worker result path hardcoded `source: 'chat'` — is this project's
first PR.

## 4. Follow the run

**Brief → Queued → Claimed → Running → Landed → Delivered**, with requeue on a lapsed
lease while attempts remain.

1. **Brief (synchronous, cheap).** Activating the tool opens the existing ToolPanel
   with its context card plus a small brief form: question, scope and constraints,
   depth. The user reviews and hits **Run**. This preserves the §9 guardrail the
   Phase 3 doc carried forward — writes into the execution engine go through a gate,
   and the gate here is human confirmation of the brief. No brief, no spend.
2. **Enqueue — `POST /api/deep-runs`.** Composes the run prompt from the tool's skill
   template plus the brief, writes the durable product record (`tool_runs`: id, tool,
   status, brief, result_md, error_class, user_email, chat_id, job_id, attempt,
   timestamps), and enqueues `dispatch_jobs` kind `work_item` with
   `payloadMeta { toolRunId, userEmail, effort?, model? }` and a deadline ≈ 2× the run
   budget (research 15 min, think 8 min; env-tunable) so time queued behind another
   run doesn't eat the run itself. Two contracts respected by construction: dispatch
   content stays *transient* (scrubbed on delivery), so the report's durable home is
   `tool_runs`, not the queue; and the *ledger* stays provenance-only — `RunSource`
   is an open union (`lib/runs.ts:35`), so `source: 'tool'` joins with zero migration
   and deep runs appear in the Phase 3 execution feed for free. Quiet win:
   `tool_runs.user_email` is attributed from the session on day one — deep runs are
   born with the attribution chat ledger rows still lack (Phase 3 §6.5).
3. **Execute (desktop, allotment).** The operator raises `WORKER_WORK_SLOTS` from 0
   to 1 — the single env flip that turns the lane on. The worker claims, heartbeats,
   and runs the same `lib/agy.ts` gateway every phase is built on. Deep Research
   relies on what makes the desktop placement valuable: agy holds the operator's MCP
   tools and web access *there*, on a residential IP, with permissions auto-approved
   in headless mode. Deep Think passes `effort: 'high'` and needs no tools. No worker
   binary changes are required.
4. **Land.** `postResult()` (`lib/dispatch-store.ts`) is the single write path for
   worker outcomes, already idempotent under retries. Extended: when the job carries
   a `toolRunId`, the report is upserted into `tool_runs` and scrubbed from the queue
   row **in the same transaction** (work items have no waiting reader, so leaving
   `result_text` undelivered would trip the orphan sweep into double-ledgering).
   Empty text remains failure — Phase 0 doctrine is transport-independent. Per the §7
   gap list, `reapExpired()` marks the `tool_runs` row failed with a typed class when
   attempts run out; a deep run must never simply vanish.
5. **Watch (poll, honestly).** The client never holds a request open — POST returns
   the run id; the panel polls `GET /api/deep-runs/:id`. agy emits nothing until a
   run completes, so the honest progress display is **state, not percentage**: queued
   (position), running (attempt n/3, elapsed, lease freshness), landed. Because the
   run is durable, the user can close the panel or refresh; an unfinished run is
   offered for reattach on return. No fabricated progress bars.
6. **Deliver.** On success the panel renders the report; the Hub also appends a short
   assistant pointer message to the originating chat (conversations are durable since
   Phase 2). Two actions: **Save** into the existing `tool_artifacts` store (tenant-
   and role-scoped, pgvector-embedded — finished research becomes retrievable context
   later), and **Insert into chat**.

## 5. The two skills

Both tools are authored as skills in the existing suite —
`hub/skills/enterprise-ai/deep-research/SKILL.md` and `deep-think/SKILL.md` — and
registered in `SKILL_CATALOG`, which enrolls them in the suggestion machinery
automatically. The skill body is the run-prompt template, not a chat lens:

| | Deep Research | Deep Think |
|---|---|---|
| Protocol | Decompose the question → parallel search passes → triangulate sources (agree/disagree, recency, authority) → cited synthesis | Enumerate framings → steelman the strongest case each way → self-critique pass → conclusion with confidence and what would change it |
| agy options | defaults; tools live | `effort: 'high'`; no tools needed |
| Deadline default | 15 min | 8 min |
| Report sections | Findings · Sources · Confidence & gaps | Conclusion · Reasoning · Counterarguments · Open questions |

One deliberate break from the incumbent tools: **no new regex scraping.** The skill
instructs agy to end the report with a fenced JSON block containing the structured
result; the panel parses that and falls back to rendering the raw markdown when
parsing fails. `parseToolArtifacts.ts` is the most fragile part of the current tool
system; new tools shouldn't inherit it, and the old ones don't need migrating.

## 6. Featuring — what "more prominent" means concretely

Today, tools are reachable *only* through the AI-suggested popover
(`SkillsPopover.tsx:71-74` filters the catalog to suggestions and renders an empty
hint otherwise). There is no static browse at all, so "featured" is a structural
change, not a sort order:

1. **Composer-level presence.** Deep Research and Deep Think get persistent chips in
   the composer area, following the precedent the EXA toggle set for a first-class
   mode affordance. One tap opens the brief panel. Every other tool waits to be
   suggested; these two are always one tap away.
2. **A pinned tier in the popover.** A "Deep" section renders at the top
   unconditionally, with suggested tools below — which also fixes the popover's
   dead-empty state before any suggestion exists.
3. **Honest availability.** The chips reflect the engine: worker fresh
   (`workerFresh()`, the same ~5 ms read chat uses) → live; worker stale → a visibly
   disabled state, "engine offline — runs on your desktop worker." A featured tool
   that silently queues into a dead worker would burn trust in exactly the surface
   being promoted.

## 7. Guardrails

- **Chat is untouched.** Separate slot pools, separate kinds, no shared budget.
  Recommended slots to start: `WORKER_CHAT_SLOTS=3`, `WORKER_WORK_SLOTS=1`.
- **Allotment-only, fail honest.** No metered fallback for deep runs in v1. Chat
  falls back because chat can't fail; a deep tool *can* — with a typed error and a
  retry affordance. A silent metered fallback would reintroduce §1's failure mode at
  up to 20 minutes of API spend per run. (A later, explicit "run metered instead —
  est. $" choice is compatible; it must never be implicit.)
- **Bounded spend.** Per-user cap of one active deep run (v1), the lane's existing
  10-job queue cap, ≤3 attempts per run, deadlines enforced by the reaper, and every
  attempt ledgered.
- **Cancelable.** Run detail exposes cancel → existing `cancelJob()`; the worker
  aborts within one 30 s heartbeat, which is where allotment stops burning.
- **Reruns are safe.** At-least-once semantics rerun a lapsed research job; both
  tools are read-only (reports, no side effects), so idempotency is trivial — the
  CAS keeps exactly one landed result.
- **Content placement.** Briefs and reports live in `tool_runs` / `tool_artifacts`
  (product tables, access-controlled); the queue scrubs content on delivery; the
  ledger keeps fingerprints only. Each store keeps its existing contract.

## 8. Execution plan — four PRs, one probe first

Same doctrine as every phase of this migration: *prove the one unproven assumption
before building on it.* Here that assumption is that headless `agy -p` actually
exercises tools (web fetch) usefully on the desktop worker. Everything else in this
design is verified against shipped code; that one thing is not yet.

| PR | Contents | Gate |
|---|---|---|
| **A — prove the lane** | Reap ledgering for work items (+ `promptFingerprint` passthrough in `lib/runs.ts`); result-route `source` derived per kind (`workItemRunSource`) with `recorded` work items ledgered by the route (they have no waiting reader); `/api/admin/work-probe` — enqueue a marker work_item requiring a live fetch of a current-time API, verdict = marker round-trip AND a timestamp within ±20 min of now (a model without tools has no wall clock). Run with `WORKER_WORK_SLOTS=1`. | PASS ⇒ everything downstream is buildable. FAIL ⇒ staged fallback (below) before any UI exists. |
| **B — run substrate** | `tool_runs` table; `/api/deep-runs` POST / GET / cancel; landing hook in `postResult()`; reap → `tool_runs` failure marking. | A round-trip run lands durably; survives refresh. |
| **C — the tools** | Two SKILL.md protocols + catalog entries; brief form; DeepResearchPanel / DeepThinkPanel (JSON-block parse, markdown fallback); poll states; save + insert actions. | Both tools produce saved reports end-to-end. |
| **D — featuring** | Composer chips with availability state; pinned "Deep" popover tier; completion pointer message into the chat transcript. | Reachable in one tap; offline state honest. |

All PRs land as real (non-draft) PRs, green on typecheck + vitest + Playwright.
Operator actions: set `WORKER_WORK_SLOTS=1` on the desktop worker — nothing else new.

**If PR A's probe fails** — headless agy can't drive tools — the staged fallback
keeps both promises partially: the Hub runs the retrieval passes itself through the
EXA search API (already integrated) and feeds the gathered material into a plain-text
agy synthesis run on the allotment. Metered search-API spend, allotment LLM spend.
The chat-lane rule that EXA turns skip agy is an interactive-routing decision, not a
ban on agy synthesizing search results inside a deep run. Deep Think is unaffected
either way — it needs no tools.

## 9. Decisions taken, with the forks left open

| Fork | Decision |
|---|---|
| Transport | `work_item` lane. Raising chat-lane timeouts was rejected: it dismantles the never-stall ladder protecting chat to serve a workload that isn't chat. |
| One run vs. staged pipeline | **Default: one run.** v1 is brief → single long run → report. A staged pipeline (plan → search passes → synthesis as separate work items) buys real progress display at meaningful orchestration cost — the natural v2, and §8's fallback already builds half of it if needed. |
| Metered fallback | **Default: none.** Fail honest with retry (§7). Flip only to an *explicit, priced, per-run* user choice — never implicit fallthrough. |
| Where results live | `tool_runs` is the system of record; `tool_artifacts` on explicit save; a pointer message in the chat transcript. The queue and ledger keep their content-free contracts. |
| Access | **Default: all staff roles.** Runs are session-attributed from day one, so staff scoping is a filter, not a policy question. Per-user concurrency cap 1. |

## 10. Risks

- **Headless tool use is unproven** — the design's one real unknown; PR A settles it
  for a few tokens, with §8's staged fallback as the escape path.
- **Long-run behavior of `agy -p`.** Print-timeout and envelope handling are proven
  at chat length, not at 15 minutes. The probe should also run one deliberately long
  prompt; `AGY_PRINT_TIMEOUT` and the worker budget both derive from the job
  deadline, so the knobs exist.
- **Rerun spend.** At-least-once × 3 attempts means a flaky desktop can spend ~3× a
  run's tokens. Bounded by design (caps, deadlines, ledger visibility), accepted as
  the price of reliability.
- **Undocumented-surface risk, inherited.** The standing caveat on the whole agy
  approach applies unchanged; the kill switch is the same env ladder as dispatch.
- **Intent landmine, avoided.** Deep tools deliberately bypass Interview Mode
  intents, so they do not touch the fail-open `isPaperclipIntent` predicate
  (Phase 3 §6.2). If they are ever routed through interview intents, invert that
  predicate first.
